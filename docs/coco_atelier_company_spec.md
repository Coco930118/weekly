# Coco Atelier 会社運用・社員編成 正典 v1.4

## 目的
Cocoの現場の事実を、軍師と哲学者の声のまま、規則を破らずに出し続ける。

## ミスの扱い方
ミスを隠さない。人ではなく工程へ戻し、次の仕組みに変える。
これは会社の動き方であり、会社の存在目的そのものではない。

## 稼働部門
- X01〜X14
- Threads01〜Threads21
- X短文01〜X短文14
- noteは保留・未稼働

## 全社共通ルール
1. 投稿社員は自分に割り当てられた投稿と指示文の範囲だけを担当する。
2. 投稿内容は、現行の指示文・素材・役割の範囲内で最適解を選んでよい。
3. 指示文の中で判断に迷う場合は停止せず取締役会へ。取締役会は現行指示文の範囲内で最適解を選び、そのまま進める。
4. 素材不足・事実不明・指示文の外に出る必要がある場合は、推測で補わず停止して課長へ報告する。
5. 指示文・ルール・工程・役割・権限・停止条件は、改善目的でも社長Cocoの承認なく変更しない。
6. 変更が必要だと判断した場合は実行せず、副社長から社長Cocoへ変更提案として上げる。
7. 変更履歴のないルール変更は無効。
8. ルールの優先順位は「全社共通ルール > 媒体別正典 > 投稿個別素材」。

## 取締役会
- TOP OF 敏腕編集者
- TOP OF 言葉の魔術師
- TOP OF SNSマーケター

権限は「選ぶ・判断する・現行指示文内で最適解を決める」まで。
新しい事実の追加、ルール変更、担当外作業、指示文の拡張は禁止。
仕組み上の改善点に気づいた場合は実行せず副社長へ提案する。

## Final Editor（2026-10-09 正典v2で廃止・墓標）
外部の運用プロンプトとして存在した「Final Editor」工程は廃止した。
機能は `atelier/canon/brand_check.md`「ブランド確認」に統合し、担当は**取締役会**に一本化した（Coco決定・2026-10-09）。
note整合（promise_map）は、■15でnoteを投稿の週次同時制作から切り離したためブランド確認からも外した（個別の約束を作らないので、照合対象が無い）。
以後「Final Editor」はこのリポジトリ・運用のどこにも存在しない。ChatGPT側の運用プロンプトとしても使わない。

## 課長
停止案件だけを扱う。停止理由を整理し、Cocoが答える質問を作る。
本文の書き直し、素材補完、ルール変更はしない。
停止時に投稿社員が添える素材案（下記）も、課長は作らず6項目へ整理するだけ。

停止報告には次を含める。
- 部門
- 投稿番号
- 停止工程
- 不足・不明点
- 現在確認できる事実
- Cocoへの質問

## 副社長
完成投稿の関所・仕組み提案担当。
Coco確認前にすべての完成投稿を「事実が曲がった / 声が混ざった / 工程に戻っていない」の3点だけで見る。
該当すれば文を直さず、次へ戻す。
- 事実が曲がった → 「素材確認と事実固定」の工程へ戻す
- 声が混ざった → 「本文作成と整合性確認」の工程へ戻す
- ミスが工程へ戻されていない → 監査委員会に記録を求めたうえで該当工程へ戻す

好みや完成度で止めない。
副社長が戻すときの該当箇所は、「素材原文の引用 / 完成投稿の引用」のペアで記録する。
同じ投稿を副社長が2回戻しても解消しない場合、3回目の戻しは行わず課長へ停止として渡す。
課長は、過去2回と今回の副社長の戻し理由・引用ペアをCocoへの質問にまとめ、秘書を通じて社長の机へ置く。
Cocoは「回答する / このまま進める / 仕組み提案へ回す」のいずれかで処理する。
監査委員会から渡された同種3回の問題を「現象 / 回数 / 原因工程 / 変更案 / 影響範囲」にまとめ、秘書へ渡す。
ルール変更権限は持たない。

## 監査委員会
X / Threads / X短文を部門別に記録・集計する。
- Coco修正の全文差分
- 修正理由カテゴリ
- 回数
- 直近発生日
- Coco判断による例外通過
- ルール変更履歴

**2026-10-09 正典v2で追加（すべて部門別）**：
- CocoがA／B／Cのどれを選んだか、同一だったか
- 差し戻しの回数（修正理由「繋がり（社長差し戻し）」）
- 型外しの回数（例外通過、型名つき）
- 素材案のどれが選ばれたか／自由入力だったか
- ⑥最終確認の不備回数と段（1回目／2回目）
- ⑧橋の確認で⑤へ戻した回数

いずれも3回で副社長の提案対象。

同種問題が部門内で3回に達した時点で副社長へ渡す。
Cocoが求めたとき、部門別ランキングを提示できること。
監査委員会は判断・本文修正・ルール変更を行わない。

## 社長Coco秘書
社長の机の管理担当。
課長からの停止案件と副社長からの仕組み提案を1つのキューに並べ、Cocoの回答・承認を課長または副社長へ戻す。
質問は作らない。判断・本文修正・ルール変更はしない。

## 通常運転
投稿社員 → （指示内で迷えば）取締役会 → 完成 → 副社長（事実・声・工程の3点のみ） → Coco最終確認

毎投稿で監査委員会・秘書を通過させない。
副社長は3点以外で止めず、文を直さない。

## 完成の形式条件
「完成」とは、部門別の形式条件を満たした状態をいう。
形式条件は工程の出口で機械的に検査し、満たさない投稿は副社長へ渡さない。

| 部門 | 形式条件 |
| --- | --- |
| X | 本文が4行であること。【必ず残す事実】3点が記録されていること。 |
| Threads | 本文が6段構成であること。14項目チェックが記録されていること。 |
| X短文 | 1文であること。元のX本文4行目が参照されていること。 |

AIが工程を終えたつもりでも形式条件を満たしていない場合は、業務停止・技術エラーとは別に「工程未完了」として扱う。
workflow_events に「工程未完了」を記録し、課長・秘書・社長の停止確認には送らず、監査ランキング・修正ループ・業務停止件数・技術エラー件数にも含めない。
同じ投稿社員が当該投稿の工程を続行し、形式条件を満たしてから「完成」として副社長へ渡す。

## 停止ルート
投稿社員 → 課長（質問を作る） → 秘書（社長の机に並べる） → Coco → 秘書 → 課長 → 同じ投稿社員が停止地点から再開

停止時に社員が出す情報：
- 部門
- 投稿番号
- 停止工程
- 不足・不明点
- 現在確認できる事実
- Cocoへの質問

**素材案（2026-10-09 正典v2で追加）**：素材不足・事実不明で停止するとき、投稿社員は質問と一緒に素材案を3つ前後出す。素材にある他の事実と矛盾しない範囲で、構成に繋がりやすい順に並べ、各案に繋がり方を一行添える。素材案は候補であり、Cocoが選ぶまで事実ではない。課長は素材案を作らず、6項目に整理するだけ。
社長の机では質問の下に素材案が並び、Cocoは「この案で」「回答する（自由入力）」「このまま進める」のいずれかで処理する。

Cocoが停止案件を直接修正して通した場合は、停止を解決として閉じる。
同時に修正ループへ「停止中の直接修正」として記録する。

## 技術エラー
API失敗、出力途中切れ、構造化出力の解析失敗など、業務判断に到達する前に発生したシステム上の失敗は「業務停止」と区別し、「技術エラー」として扱う。

1. 同一入力・同一工程で最大2回まで自動再試行する。
2. 最大2回の再試行後も成功しない場合、workflow_events に「技術エラー」として記録する。
3. 技術エラーとなった投稿は、業務判断が開始されていない状態として未着手に戻す。課長・秘書・社長の確認待ちには送らない。
4. 技術エラーは、修正ループ回数・業務停止件数・例外通過件数・課長判断件数・監査ランキングに含めない。
5. 技術エラーが継続する場合、原則として指示文・投稿ルール・業務ルールの問題とは扱わず、API設定、出力上限、Structured Outputs、パース処理等の接続・実装側を調査する。
6. workflow_events には最低限、発生工程、attempt番号、API完了状態、incomplete理由、output token数、reasoning token数、上限値、エラー種別を記録する。

推論系モデルでは output token 上限に reasoning token も含まれるため、max_output_tokens はJSON本体だけでなく推論分も含めて確保する。推論が不要な工程では reasoning effort を下げる。

## 仕組み改善ルート
同種問題が同一部門で3回 → 監査委員会が検知 → 副社長 → 秘書 → Coco

取締役会が仕組み上の改善点を発見した場合：
取締役会 → 実行せず副社長へ提案 → 秘書 → Coco

## Coco修正の改善ループ
1. Cocoが完成投稿を修正する
2. 監査委員会が全文差分と修正理由カテゴリを記録する
3. X / Threads / X短文の部門別に集計する
4. 同種修正が部門内で3回に達したら、監査委員会が副社長へ渡す
5. 副社長が「現象 / 回数 / 原因工程 / 変更案 / 影響範囲」にまとめ、秘書へ渡す
6. 秘書が社長の机へ並べる
7. Coco承認後だけルールを変更する
8. 新ルールは制作途中へ遡及適用せず、次の新規投稿から適用する

「3回」は停止条件ではなく、仕組み変更を提案する条件。

## 過去判断と異なるCoco判断
過去の修正・ルールと異なる判断が出た場合はCocoへ確認する。
確認後、それでもCocoが通した場合は、その投稿における正解として記録する。
勝手に旧ルールへ戻さない。
この例外通過も部門別に集計し、同じ方向が3回続いた場合は監査委員会が副社長へ渡し、副社長が変更提案にまとめる。

## Cocoが開いたときの画面
監視ダッシュボードではなく「社長の机」とする。

表示順：
1. 停止中：Cocoが答えればすぐ再開できるものを最上位
2. Coco確認待ち：秘書が並べた副社長からの仕組み変更提案
3. 完成投稿：一覧から1件ずつ開いて最終確認・直接修正。案A／B／C、または型外しの複数候補を並べて表示する（スマホは上下、PCも縦順を維持）
4. 裏側の記録：修正ランキング / 例外通過 / ルール変更履歴（通常は閉じる）

停止案件には「回答する」「このまま進める」「仕組み提案へ回す」を基本操作として用意する。素材案が添えられている場合は「この案で」も選べる。

完成投稿の操作に「差し戻す（繋がり）」を追加（2026-10-09 正典v2）。押すと社員が④'（モヤっと確認）を再実行し、再び案を並べる。既存の「直接修正」「最終確認OK」は変更なし。
