### 思考の型（この型に合わない文はCocoの文ではない）
①軸ずらし（最重要・二択のどちらも選ばず三つ目の軸）②判定先出し（組織側は一語で結論から）③問いで返す（関係側は答えを相手に返す）④逆転の定義 ⑤事実と感情の分離 ⑥選ばせる（2択） ⑦どっちでも構文 ⑧迷いは答え ⑨存在の格上げ

### 運用
Codeは素材から下書きを起こし、**Cocoが赤ペンで最終判断**する。判断に迷う箇所は勝手に埋めず、空欄か選択肢でCocoに返す。

### 実体験・処方の続きの都度供給ルール（2026-08-02合意）
実体験と会員帯の「処方の続き」は、**Cocoが都度渡す**方式で運用する。
- X/Threads投稿・note作成時に、実体験や処方があると効く箇所をCodeが特定し、**【実体験募集】どの投稿の・どの位置に・何の場面が要るか**を具体的にリクエストする（創作は一切しない）。**リクエストの書き方は `CLAUDE.md`「Cocoへの質問の作法」に従う。ここに条件を書き写さない**（2026-08-31：この括弧が「粒度の例を示す」を持っており、同日Coco決定の「粒度の見本を先に書かない」と正面から食い違っていた。全媒体ルールの複製は、必ず片方が古くなる）
- 受け取るまでは、その箇所を汎用の言い回しで成立させるか、空欄で返す（実体験の有無で公開を止めない）
- 受け取った実体験はエピソード在庫（episodes_soshiki.json）に採番して登録してから使う

#### 素材を、具体的な場面に翻訳しない（2026-09-03 Coco決定・恒久ルール／全媒体）

**素材が抽象なら、抽象のまま書く。** 場面に落として書き直した瞬間に、**素材に無い事実が生まれる。** しかも創作しているつもりが無いので、**いちばん見つけにくい**。

- **具体は、わたし（Coco）の側ではなく、読者の一手（「今日ひとつ」）の側に置く。** わたしの側の具体は素材に縛られるが、読者に渡す一手は素材の外から作ってよい
- **⚠️「比喩をやめて、具体的場面とともに」（2026-09-03 Coco指示）とぶつからない。** あれは**具体を置く場所の指定**であって、具体を減らす話ではない。**減らすのはわたしの側の具体だけで、読者の一手はむしろ具体にする**
- **既存の歯止めは数字だけを守っていた。** 下の `rules/posts.md`「経過・回数・期間の数字を、ゼロ主語で書かない」は**数字**が対象で、**場面の具体化は素通りしていた**。同じ形の穴が、数字と場面の2つあった
- **実例（th_03・2026-09-03）**：E372 の「決めるのが、相手の出方じゃなくて、**自分の時間の使い方**のほうになった」を「**送ったあとに夜の予定を先に決める**」と場面にした。その一行が「**行動が変わった**」という素材に無い事実を作っている。実際は「やっていたことは今と変わらない。違いは、気にしているか気にしなくなったか」（Coco受領）

#### 素材が、書いたものとぶつかることがある（2026-09-03 Coco決定・恒久ルール／全媒体）

**受け取った素材は、穴を埋めるとは限らない。書いたものの逆側にあることがある。** 素材が無いところは七つの原理から組み立てるが、**原理から作った処方は、その動きの「きれいな形」に着地する。** Cocoの実際には、きれいな形が落とした一段が入っている（夜に打つ／連絡しない／タイミングが先／黙っている人にこそ聞く）。**だから逆になるのは偶然ではなく、毎回起きうる。**

そして受け取った側は「足す」処理をしてしまう。**段落を一つ入れて、背骨は古いまま残る。足した本人は理由を持っているので、読み返しても違和感が出ない。**

1. **入れる前に、補強かぶつかりかを判定する。** 「この素材は、いま書いてあることと同じ向きか」を先に決める。**判定しないまま入れると、必ず足す処理になる**
2. **ぶつかるなら、段落を足さない。処方の一手から直す。** 背骨を差し替えるのであって、例外を1つ添えるのではない
3. **直したら、同じ向きを持っている場所を全部たどる。** **たどる手順は `rules/check.md`「ルールを直したら、その数字と方針の出どころと行き先をたどる」が正典。ここに手順を複製しない**——引き金がルールか素材かの違いで、やることは同じ。**実際に置き去りになったのは、見出し・タイトル・締め・変化までの時間感、そして記事やJSONが自分を説明している項目**（noteなら `practice_tool` `framework` `outcome_promise` `description` `sns_hooks`、投稿なら `quote` と返信）
4. **判定と反映は、入れた本人以外が読み返す。** 別のセッションが読む枠は `CLAUDE.md`「週次は三段階でひとつ」にある

- **機械では見つからない。** `note_check.py` の約束と回収は `promise_map` のキーと見出しが在るかしか見ておらず、**向きは見ていない**。下の実例3件はどれも0件で通っている
- **実例（2026-09-02〜03 の2日で5件）**：note_2026-09-02_morning（「夜のうちに打つ」と「翌朝に書く」が同じ無料エリアに逆で並んだ）／note_2026-09-03_order（E403訂正後も「その日のうちに全部話す」が冒頭に残った）／note_2026-09-04_autumn（投稿は「連絡しない」、noteは「一件だけ送る」）／**x_05**（E437 と逆の「黙っている人に振ると罰に変わる」を、素材に無いまま書いていた）／**th_07**（E403訂正後も「その日のうちに全部話す」）。**5件とも、見つけたのは書いた本人ではない**

## エピソード管理ルール

### ファイル
| ファイル | 役割 |
|----------|------|
| `reference/episodes_soshiki.json` | エピソード本体（E1〜En。E210〜E249は回答素材・原文ママ） |
| `reference/episode_usage_log.json` | 使用履歴（`log`）＋登録記録（`registered`）＋**在庫なしテーマ（`no_stock`）** |
| `reference/coco_voice_source.json` | Coco素材集（思考の型・語彙・帯ルール・エピソード在庫） |

### 新規投稿生成時の手順

1. `episode_usage_log.json` を読み込む
2. 各エピソードの直近使用日を確認
3. **直近30日以内に使用したエピソードは除外**（使用日リストの最新値が今日-30日より新しければ除外）
   - **例外**：`registered` で `type: 日常素材`・`exempt_30day: true` が付いたバッチ（現在は E373＝Cocoの生活・嗜好素材）は30日除外を適用しない（2026-08-25 Coco決定）。使ったら `log` への追記は通常どおり行う
4. 残りのエピソードからランダムに選択して各投稿に割り当てる
5. 使用したエピソードIDと投稿日を `episode_usage_log.json` に追記
6. 更新したログファイルを main にプッシュ

### 使用履歴の台帳は `episode_usage_log.json` だけ（2026-08-29 Coco決定・恒久ルール）
**`episodes_soshiki.json` の `used_in` は廃止した。** `log` が per-post で全項目（episode_ref／date／theme／platform／week）を持っており、`used_in` は同じ情報の二重帳簿だった。更新主体がルールに書かれておらず、実際に食い違いが出ている（2026-08-29：th_15 の素材を花→ヨガに直したとき、`log` だけ直って `used_in` が花のまま残った）。
- **使用履歴を書くのは `episode_usage_log.json` の `log` だけ。** エピソード側に使用実績を書き戻さない
- **30日除外が数えるのは「投稿として世に出た使用」だけ**（2026-08-29 Coco決定・恒久ルール）。`platform: "note"` の記録＝「noteがその素材を引いた」は別種で、30日判定に入れない
  - 理由：移行前の `log` に note 単独の記録は0件で、noteは「X（note化）」の形で投稿側に付いていた。used_in から移した3件を30日判定に混ぜると、**生成時に存在しなかった基準で過去週を落とす**ことになる（実例：9/1週 th_03 が E372 で落ちた。生成時の判断は正しく、台帳が割れていたのが原因）
  - 記録としては `log` に残す。落とすのは判定の対象からだけ
- 廃止時に、`log` に無かった9件（9/1週の記録漏れ6件＋E372のnote3件）は `log` へ移してから削除した

### エピソード追加時
- `episodes_soshiki.json` の `episodes` 配列に追記（ID採番: E6, E7...）
- `episode_usage_log.json` に新IDを空配列で追加
- 両ファイルを main にプッシュ
- **追加した全エピソードを、チャットに「コピペできる形」で必ず出す**（2026-08-24 Coco決定・恒久ルール／下記）

#### 追加エピソードの共有フォーマット（2026-08-24 Coco決定・恒久ルール）
エピソードを新規登録・分割登録・内容更新したら、**そのたびにコードブロック（```で囲んだ塊）でチャットに出す**。Cocoがコピーボタン一つで他セッションに渡せる状態にするため。要約や箇条書きの散文で済ませない。
- **既定は「そのセッションで更新した全エピソードを、1つのコードブロックにまとめて出す」**（コピーボタン1回で全部渡せる形）。エピソードごとに区切り線（`----------`）を入れて読み分けられるようにする
- **1エピソード＝1ブロックに分けるのは、Cocoから都度指示があった時だけ**
- 出す項目は次の順で固定する：
  1. 見出し行 `【エピソードE◯◯◯】タイトル（用途）` ＋ 受領日と登録先ファイル
  2. 種別／カテゴリ／帯／テーマ
  3. 中身（`key_phrases` の全項目）
  4. 使用条件（`usage_limit`）
  5. 事実ルール（`verbatim_rule`）
  6. 注意（`usage_note`。Cocoから受けた訂正・書き方の指摘もここに含める）
  7. 使用実績（`episode_usage_log.json` の `log` から引く。未使用なら「なし」）
  8. 背景（なぜこの素材が要るのか。他セッションが用途を誤らないため）
- 内容を後から訂正した時も、**訂正後の全文を同じ形で出し直す**（差分だけ伝えない。コピペで上書きできる状態を保つ）

### エピソード分割ルール（自動適用）
「新しいエピソードを預けます」で受け取ったエピソードが複数の原則・思考を含む場合、**確認なしで自動分割して登録する**。
- 1エピソード＝2〜4原則を目安とする（意味的にまとまる単位で切る）
- 分割後のIDは末尾から連番（例：E57追加後はE58, E59…）
- 各分割エピソードに `title` / `theme` / `key_phrases` を付ける
- 分割した全エピソードをまとめて1コミットで main にプッシュ

#### 分割の判断基準（必ず適用）
同一エピソード内の原則が「投稿の核心メッセージとして独立して成立するか」で判断する。

**分割が必要なケース（1投稿に混在すると読者に伝わらない）**
- テーマの主体が異なる：「自分の回復」と「他者への関わり方」
- 行動の方向が逆：「関与しない」と「どう関わるか」
- 概念の領域が別：「戦略的ポジショニング」と「コミュニケーション技術」
- 実話が複数の独立したシーンで構成されている（混在すると投稿が拡散する）

**同一エピソードに収めてよいケース**
- 同じ技術・手法の複数ステップ（例：言葉の設計術4種）
- 同じ状況での連続した判断（例：厳しさを渡しつつ労いも渡す、同日の出来事）
- 同じ「〜はしない」系の並列原則（例：擁護もしない・排除もしない）

**実話エピソードの場合**
- 別々の日・別々の相手・別々のシーンは原則1話ずつ独立させる
- 同じ相手・同じ文脈での一連の出来事は同一エピソードに収めてよい

### 除外エピソードが全て埋まった場合
使用可能なエピソードがゼロになったら、最終使用日が最も古いものから順に再使用する。
